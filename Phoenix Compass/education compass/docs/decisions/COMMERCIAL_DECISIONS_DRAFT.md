## OD-07｜退款政策 · P1

**现状**：退款只能由管理员通过服务端接口发起，需 RBAC、幂等键和理由；退款成功后自动撤销该订单的报告权益；不向用户开放自助退款。

**建议决策**

1. **保持不开放用户自助退款。** 客服人工受理，管理员接口执行。
2. **退款窗口：支付后 7 天内，且未下载过 PDF。** 已下载视为已消费完毕。
3. **不做部分退款。** 单价 ¥39.90，部分退款的对账成本远高于金额本身。
4. **退款后撤销权益，不恢复。** 保持现有安全默认值。
5. **例外：因我方原因（来源目录撤回、报告事实错误、系统故障导致无法交付）全额退款，不受 7 天与下载状态限制。**

**理由**：数字内容一经交付即难以收回，7 天加未下载是可自动判定的客观标准，避免逐案争议。第 5 条是必要的，
因为运维手册已明确规定"不得以拒绝交付代替退款"——出了内容事故必须能退。

**✅ 已实现（2026-09-23）**：管理员退款接口现在校验两条：支付后 7 天内、且从未下载过 PDF。
因我方原因退款时传 `policyException: "MERCHANT_FAULT"` 豁免，并在审计记录里留痕。

实现时补了一个缺口：**PDF 下载此前完全没有留痕**，"未下载过"无从判断，所以迁移 008
给 `reports` 加了 `pdf_first_downloaded_at`，只记首次下载。

两个刻意的例外：
- **已在途的退款重试不受政策约束**——否则会把它卡死在 `REFUNDING` 中间状态。
- **账号注销后订单与报告脱钩，查不到下载状态时不阻断**——用我方的删除行为去拒绝用户退款说不过去。

## OD-08｜报告访问期限与账号注销 · P1

**现状**：权益无自动到期，报告永久可访问；账号注销已于 2026-09-23 实现（本项提出时尚不存在）。

**建议决策**

1. **已购报告永久可访问**，不设到期。
2. **PDF 下载不限次数**，但下载链接保持鉴权，不产生公开 URL。
3. **账号注销：必须在正式上线前实现。** 注销后删除家庭、学生、问卷、报告、AI 对话；
   保留订单与支付记录的**最小财务字段**（订单号、金额、时间、交易号），因为会计与税务法规要求留存交易凭证。
4. **注销为不可撤销操作**，需二次确认并明确告知已购报告将一并删除。

**理由**：一次性购买设到期会显得苛刻，永久访问的存储成本可忽略。第 3 条当时是硬性的——
起草时数据清单确认**完全没有删除路径**，而这直接关系法定删除权，所以随后就做掉了。

**✅ 已实现（2026-09-23）**：`DELETE /v1/me`，小程序「我的」页两步确认。删除个人数据、
保留脱钩后的财务凭证，细节见 [DATA_INVENTORY.md](../DATA_INVENTORY.md) §4.2。
第 3 条中"保留财务最小集"的范围仍需你确认是否符合你所在地区的税务要求。

## OD-09｜学生资料修改后如何处理 · P1

**现状**：新测评形成新快照和新订单，不覆盖已购报告。

**建议决策**

1. **保持现状**：改资料不影响已购报告，报告是购买时点的不可变快照。
2. **新测评 = 新订单，全价。** 不提供改资料后的免费重算。
3. 界面明确提示："本报告基于 {日期} 的资料生成，修改资料需重新测评并购买。"
4. **例外：购买后 7 天内，因我方规则错误导致结论有误，免费重出。**

**理由**：报告的价值在于它是某个时点的完整分析，可变会破坏证据链（每份报告都带来源目录版本和 QA 状态）。
免费重算会被用来反复刷报告。

## OD-10｜发票与客服 SLA · P1

**建议决策**

1. **上线初期不开发票。** 购买页与协议中明确告知"暂不支持开具发票"。
2. 账单商品名统一为 **"Phoenix Education Compass 单次完整报告"**（与数据库 `products.name` 一致）。
3. **客服 SLA：工作日 24 小时内首次响应**，渠道为小程序内反馈入口。
4. 退款处理时限：受理后 3 个工作日内给出结论。

**理由**：¥39.90 的个人消费场景开票需求低，而对接发票系统成本高。
关键是**说清楚"不开票"，而不是沉默**——承诺了做不到比不承诺更糟。

**⚠ 待确认**：¥39.90 是否需要开票取决于你的经营主体类型和当地税务要求，这一条建议找财税顾问确认。

## OD-11｜是否需要订单发货管理 · P1

**建议决策**：上线前按微信官方**最新**要求核对一次，不凭历史经验判断。

**理由**：微信对交易类小程序的履约要求变动频繁。更重要的是——
[WECHAT_PAY_RUNBOOK.md](../WECHAT_PAY_RUNBOOK.md) §2.1 已经指出本产品很可能要走**虚拟支付**而非普通微信支付，
而虚拟支付有自己的"发货推送"机制（`xpay_goods_deliver_notify`），**与普通支付的发货管理是两套东西**。
支付通道定下来之前，这一项没法有意义地决策。

**依赖**：先关闭支付通道选型。

## OD-13｜¥39.9 报告与 ¥199 会员的关系 · P2

**现状**：两个 SKU 和权益完全隔离，无互赠、无折扣。`PHOENIX_MEMBER_199` 在数据库中 `active = false`。

**建议决策**

1. **保持完全隔离。** 会员不包含报告，买报告不赠会员。
2. **上线初期不推出会员**，保持 `active = false`。
3. 将来若推出会员，**不追溯**：已购报告的用户不自动获得会员权益。

**理由**：会员产品本身还没定义清楚。过早绑定会在将来限制定价空间，而且隔离是可以随时放开的，
反过来（已经承诺了折扣再收回）不行。

## OD-14｜是否镜像运营数据到飞书 · P2

**现状**：`FEISHU_BITABLE_ENABLED=false`，不镜像。设计上排除支付密钥、问卷全文、openid、完整报告正文。

**建议决策**

1. **上线初期不启用。**
2. 将来启用时，**保持敏感字段开关（`FEISHU_CUSTOMER_PROFILE_FIELDS_ENABLED`）关闭**，只镜像假名化的运营统计。
3. 若确需镜像家长手机号等可识别字段，**必须先在隐私政策中明确告知，并取得逐条镜像同意**。

**理由**：[数据清单](../DATA_INVENTORY.md) §3.4 确认，开启敏感字段后会把**家长手机号、学生年龄、性别、年级、学校**
发到飞书。实体 ID 虽然做了 HMAC 假名化，但这些业务字段本身不假名化——足以识别到具体的人。
在隐私政策定稿前启用，等于在没有告知依据的情况下向第三方提供个人信息。
